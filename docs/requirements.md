# ccteam 用户需求文档

> 本文档以**用户痛点**为中心，回答一个问题：ccteam 服务的人在没有 ccteam 时，每天经历什么样的失败、疲惫和放弃。
>
> 功能、架构、agent 角色、文件协议——都不在本文档范围。所有实现决策都应回到本文档验证：是否真的解决了下面的痛点。

---

## 一、目标用户

ccteam 服务于「**想做软件、但不想（也不应）成为项目经理**」的人。

**典型画像：**

- **独立开发者 / 个人创作者**：脑袋里有 10 个想法，但精力只够做 1 个。
- **非技术背景的产品人**：有强烈的产品直觉，但写代码、装环境、调依赖会让灵感冷却。
- **想做副业 / 独立产品的工程师**：白天上班已经够累了，下班只想看到结果，不想再当 tech lead。
- **批量孵化的尝试者**：想用低成本把 10 个想法都试一遍，留下能跑的那一两个。

**他们的共同特征：**

- 把"想法 → 可运行软件"看成一个**端到端的黑盒**——不想管中间过程。
- 把 AI 当作**外包团队**，而不是**编程助手**。
- 时间稀缺、注意力稀缺，**任何需要持续在线盯着的工具都是负担**。

---

## 二、核心痛点

每一条痛点都对应一个具体的、反复发生的、让用户感到失败 / 疲惫 / 放弃的场景。

### 痛点 1：想法死于"开始"

**场景：** 周末早上想到一个不错的小工具——本地书签管理器，离线可用、按域名归类。

**接下来发生的：**
1. 纠结技术栈：FastAPI？Flask？Next.js？Electron？—— 30 分钟没了。
2. 装环境：Node 版本不对，nvm 切来切去，npm install 报错…… 1 小时没了。
3. 写脚手架……还没碰到核心功能，孩子哭了 / 该吃饭了 / 周末结束了。
4. 周一晚上回来，已经忘了自己在干嘛。项目永远停在 hello world。

**用户真正的诉求：**
> "我只想说出来，然后看到一个能跑的东西。技术选型、环境、脚手架——这些不是我想花精力的地方。"

---

### 痛点 2：AI 助手仍然要求"我"是项目经理

**场景：** 用了某 AI 编程 / AI 团队工具——它给了我一个"团队"，但每一步都问我：
- "这个 API 你想叫什么？"
- "数据模型用 SQLite 还是 Postgres？"
- "这个测试覆盖到这里够吗？"
- "我做完了 X，下一步做什么？"

**接下来发生的：**
- 一开始还有耐心，回答了 5 个问题。
- 第 10 个问题时开始烦躁。
- 第 20 个问题时怀疑：**我是不是自己写还更快？**
- 项目最终半途而废——不是因为做不出来，是**我的注意力被"管理 AI"耗光了**。

**用户真正的诉求：**
> "我说一句话，它干一周。中间不要回来找我，除非你**真的卡死**了，并且**已经试过自己解决**。"

---

### 痛点 3：测试和质量是黑洞

**场景：** AI 写完了功能代码，看起来挺像样。我跑了一下，主流程能用。

**接下来发生的：**
- 边界情况一碰就崩。
- 某个改动悄悄引入了三个 bug，我一周后才发现。
- 我已经不记得当时是怎么实现的，调试花 2 小时。
- "AI 写的代码到底能不能用？"——这个问题永远没有答案。

**用户真正的诉求：**
> "代码不过测试就**不要交给我**。测试本身是 AI 自己的事，不是给我多一项要审查的东西。"

---

### 痛点 4：bug 修复变成无限循环

**场景：** AI 修一个 bug，引出三个新 bug。我只能不断地复制错误日志粘贴回去。

**接下来发生的：**
- 一上午都在「复制错误 → 粘贴 → AI 修 → 又一个错」。
- 很多错误其实是 AI 自己应该能看到 / 解决的，但它一定要等我把日志贴过去。
- 我成了一个**人肉错误信息搬运工**。

**用户真正的诉求：**
> "你能跑测试，你能看日志，你能搜索文档。**你自己修**——修不好再来找我，并且告诉我你**试过什么**、**卡在哪**。"

---

### 痛点 5：想法太多，全部烂尾

**场景：** 一周内冒出 5 个想法，每个都开了 repo，每个都做到 30%，每个都没上线。

**接下来发生的：**
- 想推进项目 A，要先想"上次做到哪了？"——光恢复上下文就 30 分钟。
- 同时跑三个项目时，**自己也乱了**。
- 最后所有项目都死于"我已经不知道从哪开始"。

**用户真正的诉求：**
> "我今天扔进去 5 个想法。明天起床它告诉我'2 个已交付，2 个被否决（理由是 X），1 个卡在 Y 需要你决定'。我只看交付物和决策点，**不看过程**。"

---

### 痛点 6：不是每个想法都值得做

**场景：** 突发奇想要做"AI 菜谱生成器"，吭哧吭哧做了一周。
做完发现：
- 市面上已经有 5 个免费同类工具。
- OpenAI API 成本算一下根本不可持续。
- 用户根本不会下载这种小工具。

**接下来发生的：**
- 时间和热情都白费。
- 下次有新想法时，**自己内心先打了退堂鼓**——"上次也是这样兴冲冲做完没人用"。

**用户真正的诉求：**
> "在我投入精力**之前**，先有人帮我做一遍冷静的可行性评估——市场有没有人做？技术能不能做？商业上跑不跑得通？**不通过就直接否掉**，不要让我浪费时间。"

---

### 痛点 7：进度永远不透明

**场景：** AI 在后台跑，我不知道它在干嘛。

**接下来发生的：**
- 5 分钟看一次终端，怕它卡住。
- 怕它跑偏，浪费 token。
- 怕它跑完了我没注意到，错过了交付时机。
- 最终的体验是：**我在盯着 AI**，而不是 AI 在替我工作。

**用户真正的诉求：**
> "我不在的时候它自己跑，我在的时候用一句话就能知道'现在怎么样了'。所有进度都看得到、可追溯，但**不需要我主动去查**。"

---

### 痛点 8：每一步都要点"允许"

**场景：**
- 弹窗：「允许执行 npm install？」 → 允许。
- 弹窗：「允许写入文件 src/main.py？」 → 允许。
- ……一晚上点了 200 次允许。

**接下来发生的：** 我已经不记得自己点了什么，全部一路 yes。这个机制**只是给我增加了疲劳感**，没有真的保护我。

**用户真正的诉求：**
> "我已经把项目交给你了。在这个项目沙盒里，你想干什么就干什么。**不要再问我了**。"

---

### 痛点 9：AI 团队需要"人来主持"

**场景：** 某些 AI 多 agent 工具号称团队协作，但实际上：
- **主对话窗口必须开着**。
- 我必须充当 team-lead，下发任务、协调冲突、做最终裁定。
- 关掉窗口，团队就停摆。

**接下来发生的：**
- 没法在睡觉时让它跑。
- 没法在上班时让它跑。
- 这不是"AI 团队"，是"**AI 帮我打字的会议室**"。

**用户真正的诉求：**
> "团队的运转**不依赖我在场**。我下班关电脑，早上起来看结果。"

---

### 痛点 10：每个新项目都从零开始

**场景：** 做完了项目 A——踩过的坑、找到的好用的库、形成的代码模式——到了项目 B 全部清零。AI 又一次从头摸索，又一次踩同样的坑。

**用户真正的诉求：**
> "我做的项目越多，下一个项目应该**越快、越稳**。经验应该自动沉淀，不需要我手动写 wiki。"

---

### 痛点 11：关键节点不把控 = 终态发现方向错了

**场景：** 把"做个本地书签管理器，离线可用"扔进系统，关电脑出门一周。回来一看——

它给我做了个**带云同步、多用户、有评论功能**的书签平台。测试全绿、文档齐全、技术上挑不出毛病。

**但这不是我要的。**

**接下来发生的：**
- 一周时间已经烧完，token 也烧完。
- 要么接受这个偏方向的产品，要么让它推翻重做（再烧一周）。
- **关键是：plan 阶段它写"将实现云同步"的时候，如果有人/有 agent 拦一下，整周浪费就避免了。**
- 测试通过抓不到这种偏差——测试只验证"代码做了它声称要做的事"，不验证"它声称要做的事是不是用户想要的"。
- 单个 critic agent 也抓不到——它模仿"通用品味"，抓不到我对"我那个产品"的具体期待。

**为什么单 agent 抓不住、必须靠"团队议事"**：用户脑里有个**只有自己知道的 mental model**——"我要的那个书签管理器是什么样"。AI 看到的是文字 spec（spec 永远不完整，人脑里那个东西无法完整文字化）。这不是模型能力问题，是**信息论意义上的下限**——再强的单 agent 也只能从 spec 推断方向，推断本身就是猜测。但**如果换成多 agent 互检**——架构师审技术、CEO 审商业、设计师审 UX、安全官审风险——多视角各自推断，互相挑刺，**绝大多数偏差能在 agent 之间议出来；议不出共识的，才是真正需要用户拍板的**。

**与痛点 9 的区别——离场 ≠ 失联**：
- 痛点 9 拒绝的是「**持续在场当 team-lead**」（每 phase 都问"下一步做啥"）。
- 痛点 11 拒绝的是「**完全失联**」——一周内不出现一次，结果跑偏一周才发现。
- 中间地带 = **AI 团队替人开会，开不出共识时再用 30 秒推用户拍板**。

**用户真正的诉求：**
> "我不想全程在场，也不想睁眼一看不是我要的。系统应该自己有'多人审'机制：架构师审技术、CEO 审商业、设计师审 UX、安全官审风险——这些 AI 视角议出共识就过；议不出共识时，再用 30 秒推给我决策。**不是每个节点都来烦我，而是系统先开会一遍，开得出共识就走，开不出来就把 2-3 个选项摆给我点。**"

**对比佐证（gstack 等工具）**：市面上的 AI 工程辅助工具（典型如 [gstack](https://github.com/garrytan/gstack)）显式拆出 `/plan-ceo-review`、`/plan-eng-review`、`/plan-design-review`、`/ship` 四个独立命令——证明 plan 完成与 ship 前确实是不可绕的关键节点。但 gstack 要求**用户在场敲命令**——回到痛点 9。ccteam 的方案是把这个共识反过来用：**多 agent 自己跑 ceo-review / eng-review / design-review，议得出共识就过；议不出来才主动 push 用户 30 秒决策**。保留了"关键节点必须把关"的实质，删掉了"用户必须在场"的形式。

**系统设计应满足的形态（三层纵深防御）**：
- **L1 架构约束（写死的红线）**：scope budget、phase 必产出物、危险命令拦截、不可改的 invariant——deterministic、不与 agent 商量
- **L2 多 agent 互检（替代人值守的主力）**：每 phase 启用相关 audit agent（architect / critic / designer / security / scope-watcher），议出共识就过——这层处理 95%+ 决策
- **L3 用户 fork 决策（兜底）**：agent 集体拍不了板时主动 push；24h 不响应默认通过；用户 30 秒看摘要 + 点 ABC + 可选一句话 tweak；可调 agent 自信阈值（yolo / balanced / careful）
- **顺序是 L1 → L2 → L3，不是并联**——人是 last resort，不是 first checkpoint。痛点 11 的解法主路径是 L1+L2，L3 只是兜底。

### 痛点 12：工作流插件靠人手动调，效率低还调不全

**场景：** 用了一套像样的 AI 工程辅助工具——比如 [gstack](https://github.com/garrytan/gstack) 的 23-skill 工程团队包，或者 Claude Code 官方 [claude-plugins-official](https://github.com/anthropics/claude-plugins-official) 的几十个 plugin（`feature-dev` / `pr-review-toolkit` / `security-guidance` / `code-modernization` / `code-simplifier` / ...），还能加上社区的若干。

每个工具单独看都很好用：`/plan-ceo-review` 让 AI 站 CEO 视角审；`/plan-eng-review` 站架构师视角审；`/qa` 跑端到端测；`/cso` 做 OWASP + STRIDE 安全审计；`/canary` 灰度发布；`/document-release` 出文档；`security-guidance` 拦危险写文件；`silent-failure-hunter` 揪静默失败……

**接下来发生的：**
- 做完 plan，**忘了**跑 `/plan-eng-review` → 架构没审就 implement，埋雷。
- 记得跑 `/qa`，但**忘了** `/cso` → 上线后被人扫到 SQL 注入。
- 跑了 `/plan-ceo-review`，产物落在某个文件里——**没人**自动喂给 implement 阶段，得我**手动复制粘贴**。
- 项目临近交付，**没人**提醒跑 `/document-release` → 文档缺失，后续移交困难。
- 看到一个新插件叫 `/silent-failure-hunter`，挺有用，但**不知道该插在哪个 phase**——干脆不用了。
- 我加班把所有命令背下来、记每个在哪个 phase 用、记每个产物去哪里……

**等等——这不就是又当了一回 team-lead 吗？**

每个工具都解决一个具体局部问题，**但工具集体留了一个未解决的整体问题：谁来编排它们**。默认答案是"用户编排"——把"协调 agent"换形态变成"调度 plugin"，本质还是用户在做编排劳动。

**与痛点 9 的区别——劳动维度不同**：
- 痛点 9 关切的是**决策劳动**——team-lead 协调冲突、做最终裁定。
- 痛点 12 关切的是**流程编排劳动**——orchestrator 决定"何时调谁、产物给谁、有没有漏掉关键 step"。
- 痛点 9 不解决，人持续在场做**决策**；痛点 12 不解决，人持续做**记忆 + 触发 + 产物搬运**。
- 两个都是"人的劳动"，但**痛点 9 累在精神，痛点 12 累在记忆与流程**——互不替代。一个 AI 工具可能解决了痛点 9 但完全没碰痛点 12（甚至加剧——给了你 23 个新插件让你记）。

**用户真正的诉求：**
> "我不想记几十个命令、不想知道哪个在哪个 phase 用、不想手动把 phase A 的产物复制到 phase B 的输入。**整套工作流应该自己串起来——我提需求，系统自己知道下一步该 review、该 qa、该 cso、该 ship，顺序对、覆盖全、产物自动接力**。新插件出来时，系统自己判断该装到哪个 phase——不用我研究文档。"

**生态视角——这个问题只会更严重**：
- gstack 23 skills 只是开始；claude-plugins-official 几十个、社区还在持续增长。
- 越多好工具 = 越多需要编排的零件 = 用户编排负担**线性增长**。
- 不解决这个，就出现"工具越来越好但用户用不起来 / 用不全"的怪现状——好工具变成沉默资产。

**ccteam 设计的回应**：
- 9 个主干 phase 模板就是预编排好的 workflow 骨架。
- phase 协议须支持"sub-skill 自动调度"——每个 phase 在 front matter 列出本阶段应 trigger 的 sub-skills（例：ship phase 自动跑 `/cso` + `/document-release` + `/canary`）。
- ccteam 的差异化**不是**再写一遍那些 skill，**是替人 orchestrate 这些 skill**——复用 gstack / claude-plugins-official / 社区插件，调用时机由 orchestrator 决定。

### 痛点 13：大项目串行慢，并行规模选不对

**场景 A（项目过大，默认串行太慢）：** 提需求"做一个完整的 SaaS：后端 API + 前端 dashboard + 移动 app + 用户文档"。

ccteam 跑了一周——一个 implement phase 串行做完后端，再切前端，再切 mobile，再切文档。我看着进度条想：**这四件事明明可以并行**，加起来三天就够了。

**场景 B（项目太小，默认并行又浪费）：** 提需求"做个 todo list，本地存 SQLite"。

ccteam 主动开了 4 个 tmux session 并行——后端 1 个、前端 1 个、tests 1 个、docs 1 个。结果总 token 翻 4 倍，代码反而更乱（子模块边界过早划开，接口对不齐）。**这点活根本不需要并行**。

**问题的本质：**
- Claude Code 提供三档并行机制（subagent / Agent Teams / 多 session），粒度从小到大。
- 用户不该知道何时用哪个——但**必须有人决定**，否则要么慢要么浪费。
- 默认串行：大项目太慢；粗暴 always-parallel：小项目资源浪费。

**与痛点 11 L2 的区别——质量并行 vs 速度并行（很容易混）**：
- 痛点 11 L2 = 多 agent **同一输入不同视角议事**（垂直，为正确）——3 个 agent 看同一份 plan 各提意见。
- 痛点 13 = 多 agent **各做不同事**（水平，为加速）——3 个 agent 各写一份不同代码模块。
- 同样"多 agent"，但前者并行**审同一件事**，后者并行**做不同事**；不能混用一种机制兼顾两者。

**与痛点 5 的区别——项目内 vs 项目间**：
- 痛点 5 = 5 个独立项目并发推进（inbox 调度）。
- 痛点 13 = 1 个大项目内部拆 N 路加速（单项目并行结构）。

**与痛点 12 的区别——并行 vs 串行**：
- 痛点 12 = 串行 workflow 接力（plan → review → ship，不漏不错）。
- 痛点 13 = 同一 phase 内不同子任务并行（implement = backend ∥ frontend ∥ mobile）。

**用户真正的诉求：**
> "我提需求，系统自己评估这事多大、能拆几路、用什么粒度的并行。简单的就串行做，中等的 phase 内并行，大型的开多 session。**我不要知道'subagent vs Agent Teams vs 多 session'是啥——我只要进度合理快、token 不浪费**。"

**关键洞见——三档不是互斥，而是叠加层级**：

很多人误把三档当 either-or 选择。事实上**它们是叠加层级**：

| 项目尺度 | 主框架 | 叠加层 1 | 叠加层 2 |
|---|---|---|---|
| 大型（多子模块） | `multi_session`（每子模块独立 session） | `Agent Teams`（每 session 内 phase 多角色） | `subagent`（每 agent 内研究 / 单点 audit） |
| 中型（单 session 多角色） | `Agent Teams` | `subagent`（每 agent 内研究） | — |
| 小型（单线） | `solo` | `subagent`（偶尔研究 / 单点 audit） | — |

具体例子：implement phase 启动 Agent Teams，`backend-dev` / `frontend-dev` / `reviewer` 三 agent 并行；**backend-dev 内部**同时用 `Task` 工具启 subagent 研究"我们 codebase 怎么用 SQLAlchemy"。两者**同时发生**，职责互不重叠——Agent Teams 做**横向多角色**，subagent 做**纵向 context 节流**。三档机制可以**逐层嵌套**，不是 either-or。

**ccteam 设计的回应**(V0.4.0+ workflow.yaml 架构):
- **workflow.yaml 声明并行拓扑** — 每个 agent 的 `parallelism: u32` 字段决定该 role 同时可跑几个 session;`trigger: watch:<dir>/` 决定 fan-out 触发条件(每个新 artifact 一个 session)。系统**事件驱动**,无需在 plan 阶段预先决定"主框架"档次。
- **subagent 不在 workflow 协议中声明** — 任何 agent 内部都可 ad-hoc 启 subagent(`Task` 工具),不需要 workflow.yaml 许可,叠加在主框架之上。
- **三档自然落到 workflow 语义**:
  - **solo** = `parallelism: 1` + 串行 watch dir
  - **agent_team** = 同一 watch dir 多 role 监听(fan-out 一次 → N agent 并行处理) + 后续 gate trigger 收敛
  - **multi_session** = 同一 role `parallelism > 1`(同时跑 N session 处理 backlog)
- **资源约束**:`workflow.yaml::budget`(V0.4.6 F84)`max_cost_usd_per_24h` / `max_agent_spawns_per_hour` 自动 trip + auto-disable;daemon 全局 `MAX_CONCURRENT_PROJECTS: 3` 硬上限。

**边界 — 这条不解决什么**:
- 不解决**自动任务分解**(workflow.yaml 拓扑要 ccteam-creator skill / 人手工写) — 本痛点假设 workflow.yaml 已声明好 fan-out 拓扑。
- 不解决**子模块接口同步**(role 之间通过 artifact 文件协作,无 RPC/IPC 内层契约管理)。

## 三、用户对"理想体验"的描述

如果让目标用户用一句话描述他想要的工具，他会说：

> **"我说一句中文，它给我一个能跑的软件。中间它不来烦我，除非真的需要我做选择；选择题给我两三个选项 + 它的推荐，我点一下就行。"**

更具体的体验拆解：

| 维度 | 用户期望 |
|---|---|
| **输入** | 一句自然语言，不需要技术词汇 |
| **输出** | 可运行的软件 + 测试报告 + 进度记录 |
| **过程参与度** | 几乎为零；仅在 AI 自检拍不了板或系统主动 escalate 时出现 |
| **决策频次** | 极低——AI 自检处理大多数；用户上推典型 0-2 次/项目 |
| **AI 自检层** | 多 agent 互检（architect / critic / designer / security / scope-watcher）+ 架构约束（写死的红线）；agent 议出共识就过——这层处理 95%+ 决策 |
| **工作流编排** | 系统自己串主干 phase + sub-skill 自动 trigger + 产物自动接力；用户只提需求，不需要触发任何命令、不需要记任何工具放在哪个 phase |
| **并行规模** | workflow.yaml 声明 `parallelism: u32` + `trigger: watch:<dir>/`,fan-out 事件驱动;subagent 任何粒度都可叠加;用户不感知"何时用哪档" |
| **用户兜底层** | agent 议不出共识时 push：摆 2-3 个选项 + 推荐 + 一句话 tweak；24h 不响应默认通过；可调 agent 自信阈值（yolo / balanced / careful） |
| **失败处理** | AI 自己尝试 N 轮后才来找我，并附"试过什么 / 卡在哪" |
| **多项目** | 排队执行，自动推进，不需要我手动调度 |
| **离线运行** | 我关电脑/窗口，AI 团队继续开会——议不出共识时 push telegram 等我 30 秒拍板 |
| **质量保证** | 多 agent 互检 + 测试不过不交付；方向由 AI 团队议事保证，议不出来才上推我 |
| **无效想法** | 在投入开发**之前**就被否掉，附理由 |
| **跨项目沉淀** | 项目 N+1 比项目 N 更快、更稳，自动复用经验 |

## 四、非目标用户（明确不服务的人）

为了让边界清晰：

- **想用 AI 学编程的人**：ccteam 是交付工具，不是教学工具。
- **企业级团队**：复杂权限、合规、多人协作的场景不在范围内。
- **追求精雕细琢的工程师**：希望对每行代码有控制权的人，会觉得 ccteam 太"黑盒"。
- **对代码质量有强主观要求的人**：ccteam 用"测试通过"作为质量底线，不做主观代码 review。

## 五、成功判定（用户视角）

ccteam 是否成功，**不**由这些指标判断：
- ❌ 代码行数
- ❌ Agent 数量
- ❌ 技术架构先进度

**而是**由这些指标判断：

1. **从想法到上线，用户参与时间 < 10 分钟**（不含 AI 自己跑的时间；含 fork 决策时间）。
2. **一周内能并行推进 5+ 个项目**，用户不感到混乱。
3. **用户睡觉时项目继续推进**，醒来有具体进展。
4. **失败的想法在投入开发前被识别**，用户不会感到"白做了"。
5. **用户做的项目越多，下一个越快**——经验自动沉淀，无需手动整理。
6. **方向不跑偏**——多 agent 互检拦住绝大多数偏差；agent 议不出共识时，用户 30 秒拍板。终态不出现"交付的不是我要的"。
7. **零编排负担**——项目从想法到交付，用户不需要 trigger 任何 phase / skill / plugin；新工具出现时，系统自己判断该装到哪个 phase。
8. **并行规模合理**——大项目自动多 session 加速、小项目串行不浪费；solo / Agent Teams / 多 session / subagent 三层叠加由系统自动决定，用户不感知。

## 六、与"AI 团队编排工具"的根本差异

市面上已存在让用户**主持** AI 团队的工具（典型如 ccteam-creator）。它们的定位是：
> "**人类掌舵**，智能体执行。"

ccteam 的定位是：
> "**用户提需求，AI 团队替你议事并执行；议不出共识时你 30 秒拍板。**"

| 维度 | AI 团队编排工具（如 ccteam-creator） | ccteam |
|---|---|---|
| 用户角色 | Team-lead（必须在场） | 需求提出者 + agent 议事僵局时的拍板者（典型 0-2 次/项目） |
| 决策频率 | 高（每阶段都需要） | 极低——AI 自检层处理 95%+；仅 agent 议不出共识时弹 |
| 决策成本 | 每次都要看上下文、做判断 | 30 秒：看摘要 + 点 ABC + 可选一句话 tweak |
| 关掉窗口 | 团队停摆 | AI 团队继续开会（议不出共识时推 telegram 等用户） |
| 多项目 | 用户手动切换/调度 | 自动排队推进 |
| 想法可行性 | 用户自己判断 | AI 自动评估，否掉无效想法 |
| 方向校准 | 持续在场把控 | L1 架构约束 + L2 多 agent 互检 + L3 用户兜底（三层纵深防御） |
| 工作流编排 | 用户手动调命令（知道哪个何时用、产物怎么接） | 系统预编排 phase pipeline + sub-skill 自动 trigger + 产物自动接力；新工具加入由 ccteam 决定挂载点 |
| 并行规模 | 用户手动决定单线 / 多线、何时开多 session | workflow.yaml 声明 `parallelism: u32` + `trigger: watch:<dir>/`,事件驱动 fan-out;subagent 可叠加 |
| 经验沉淀 | 项目内文档 | 跨项目自动复用 |
| 目标用户 | 想当 team-lead 的人 | **不想**当 team-lead 但**仍要在 AI 团队议不出来时拍板**的人 |

**一句话总结：**
ccteam-creator 帮你**当好一个 team-lead**；ccteam 让你**不当 team-lead——AI 团队替你开会议事，议不出共识时你用 30 秒拍板**。把"持续主持"换成"偶尔仲裁"。

**关键认知（避免捡芝麻丢西瓜）**：
- 旧方案的真实价值是"**人持续在做品味与方向校准**"。把人移走的同时必须保留这部分价值——否则解决了痛点 9 却制造了痛点 11。
- ccteam 的设计公式不是「全自动 vs 人控」二元对立，而是「**L1 架构约束 + L2 多 agent 互检 + L3 用户最终 fork**」三层纵深防御。前两层让 95%+ 决策 AI 自决——这 95% 不靠"AI 听话"实现，靠**多 agent 视角互相挑刺 + 红线写死**实现。
- 人在最后一层出现 30 秒，**只在 agent 拍不了板时兜底**。痛点 11 的解法主路径是 L1+L2，**不是 L3**——L3 是 last resort，不是 first checkpoint。

## 七、本文档的边界

本文档**不**讨论：
- 具体的 agent 角色和数量
- 文件协议、消息队列、控制平面的实现
- 选用什么模型、什么平台、什么基础设施
- 版本路线图

本文档**只**确立：**用户为什么需要 ccteam，以及他们的"成功"长什么样**。

后续所有功能、架构、实现选择，都应回到本文档中验证：**是否真的解决了第二节的某一条痛点？**如果不能映射回某条痛点，就要追问——它是否真的必要？
