┌──────────────────────────── ccteam-harness ────────────────────────────────┐
│  trait HarnessAdapter(drive 轴:怎么驱动)  trait ProcessBackend(host 轴:跑哪) │
│   ├ ClaudeTuiAdapter ──┐ argv + dialect       ├ TmuxBackend(pane;resize 等 tmux 专属只在此)│

核心概念:chat ⇄ project ⇄ session(一个 chat = 你的"终端")

一个 chat bot 对话 = 你的终端。像 tmux 一样:里面可跨多个项目、随时起多 session、随时切。这是整套路由的三层关系。

  chat(一个 IM 对话)
   │  · 有一个「当前焦点」session —— 消息默认进它
   │  · 可达(ACL)若干 project
   ▼
  project(一个 dir,ccteam init 得到)
   │  · 含 0..N 个 session
   ▼
  session = project × vendor × role → 常驻 Handle(Claude tmux / Codex app-server)
            每个 session 自己的 context(/compact /clear 各管各)

路由规则 + 切换(像 tmux 切 window)

默认路由chat 内每条消息 → chat.当前 session → submit_turn
切 session@codex / /use api-svc → 改当前 session
切 project/cd payments / /project <name> → 焦点落它的默认/上次 session
新 session/new claude reviewer → spawn + 设为当前(随时可加)
列 / 看/sessions · /projects

为什么"像 CC 的 TUI"

一个 chat 就是一个"终端":多 session = 多 window,随时 /new / 切换 / 跑 slash;每个 session 独立 context + 续接。

底层对 Claude 本来就是 tmux,所以是直通不是模拟:project ≈ 工作目录、session ≈ 一个 tmux window 里的常驻 claude、chat ≈ attached 客户端、当前 session ≈ current window。

  └──────────────┘  outbound  └──────────────┬──────────────┘

        └────────────────────────────────────┤
                                             ▼
                       Claude(tmux) · Codex(app-server) … 多路复用

路由表 + 注册表

(chat,user,@bot) ⇄ session;N 渠道 × M session 双向多路复用(一人多 session、一群共享一 session)。

会话 = resume-by-id

不是常驻吊着:spawn-on-demand + 按 session-id resume + 活着就复用 + 空闲释放。状态在磁盘(transcript/turns + codex session),重启后重连 —— 比"常驻不放"安全(躲 shadow-SoT),且仍连续。

不 tick

网关循环,非 orchestrator 事件循环。progress/turns 只当展示日志。编排(flow)是另一层、推后。
transport = 一个 Channel trait(send 出站 + listen(tx) 入站)。真渠道 Telegram/Slack/微信 各一个 impl。MockChannel(push 入站 / 看 outbox)= in-proc 双向 sim,P5 e2e 直接用它驱动整条 入站→路由→submit_turn→出站(配 CCTEAM_*_BIN 假 agent,确定性)。WsChannel(WebSocket impl)一鱼两吃:跨进程 e2e + 将来 web chat 同一根线 —— UI/WS 路由在 ccteam-web(复用 pty_ws),在 cli 层用 mpsc 桥接、保持 web⊥im(不引入 web→im / im→web crate 依赖)。线缆 = ChannelMessage/SendMessage 的 JSON 镜像。纪律:e2e 永远走 Channel impl、不写分叉测试路径 —— 才能跑的是和生产同一条路。
耐久缺口(要补): 今天 IM uplink / bot-routing 是 in-proc tokio+mpsc,ccteam 重启即断。要把 supervisor/outbound 沉进 daemon,让 IM 连接也扛重启 —— 否则"云端 24/7"打折。
