# ccteam 用户需求文档

> 本文档以**用户痛点**为中心，回答一个问题：ccteam 服务的人在没有 ccteam 时，每天经历什么样的失败、疲惫和放弃。
>
> 功能、架构、agent 角色、文件协议——都不在本文档范围。所有实现决策都应回到本文档验证：是否真的解决了下面的痛点。

---

## 一、目标用户

ccteam 服务于**想把主流 code agent（Claude Code、Codex、Gemini、Pi…）的价值压榨到最大的人** —— 让**单个人**能同时驱动、编排上百个在线 agent，一个人活成一支团队。

**最大目标：让人不再成为管理 agent 的瓶颈。**

今天一个人能同时管的 agent 数，卡在他自己的注意力、记忆和手速上 —— 开几个窗口、来回复制粘贴、盯进度、逐个点允许，撑死同时管三五个就乱了。真正的天花板不是模型能力，而是**人的带宽**。ccteam 要把这个上限从"个位数"推到"上百"：人只提目标、在关键处拍板，调度、接力、并行、续跑、跨工具搬运全交给系统。

**典型用户：**

- **创始人 / 一人公司创业者**：想法和项目远多于人手，要用最少的人把它们全推起来 —— 一个人当一支团队。
- **程序员 / 工程师**：已经在用 Claude Code / Codex，但被单 session 的 context 上限、串行等待、跨工具搬运卡住，想把自己放大成"管一群 agent 的 tech lead"，而不是手动驱动一个。
- **企业员工**：想用 code agent 把自己手上的活（不止写代码）自动化、规模化，不必等团队、等排期。

**他们的共同特征：**

- 把"目标 → 结果"看成一个**端到端的黑盒**，只认交付物和关键决策，**不想管中间过程**。
- 把 AI 当作**可规模化的团队**，而不是一次问一句的编程助手。
- 真正稀缺的是**自己的注意力**：任何要求持续在线盯着、逐步点确认的工具，都会把能管的 agent 数死死压在个位数。

## 二、核心痛点

每一条痛点都对应一个具体的、反复发生的、让用户感到失败 / 疲惫 / 放弃的场景。

### 痛点 1：必须守着电脑，移动端写代码不友好

**场景：** 我被钉在电脑前才能干活。通勤路上、排队等人、晚上躺床上——这些时候脑子里冒出新想法，或者很想推进一下手头的项目。

**接下来发生的：**
- 想动手，发现 code agent 全是桌面形态——CLI、IDE 插件、终端 TUI，手机上根本打不开、跑不起来。
- 只能在备忘录里草草记一句"回去再弄"，回到电脑前热情已经凉了一半，很多干脆忘了。
- 真正能专注坐在电脑前的时间一天没几个小时，碎片时间全部浪费——**灵感和零碎时间，是我最稀缺的两样东西，却都漏掉了**。

**用户真正的诉求：**
> "我想从手机上随时下指令、看进度、拍板——电脑只是后台默默执行的机器。我人在哪、有没有坐在电脑前，都不该影响我推进项目。"

---

### 痛点 2：AI 代码质量不可信——测试是黑洞，修 bug 是人肉日志搬运的无限循环

**场景：** AI 写完了功能代码，看起来挺像样。我跑了一下，主流程能用——但只要往深处碰一点，问题就开始连环爆。

**接下来发生的：**
- 边界情况一碰就崩；某个改动悄悄引入了三个 bug，我一周后才发现，那时早忘了当时怎么实现的，调试又花 2 小时。
- 我让 AI 去修，它修一个 bug，引出三个新 bug——我只能不断地把错误日志复制、粘贴回去。
- 一上午都耗在「复制错误 → 粘贴 → AI 修 → 又一个错」的循环里。很多错误明明是 AI 自己跑一下测试、看一眼日志就能发现的，但它非要等我把日志贴过去——我成了一个**人肉错误信息搬运工**。
- "AI 写的代码到底能不能用？"——这个问题永远没有答案。

**用户真正的诉求：**
> "代码不过测试就**不要交给我**——测试是 AI 自己的事，不是给我多一项要审查的东西。你能跑测试、能看日志、能搜文档，那就**自己跑、自己看、自己修**。修不好再来找我，并且告诉我你**试过什么**、**卡在哪**。"

---

### 痛点 3：不是每个想法都值得做

**场景：** 突发奇想要做"AI 菜谱生成器"，吭哧吭哧做了一周。
做完发现：
- 市面上已经有 5 个免费同类工具。
- OpenAI API 成本算一下根本不可持续。
- 用户根本不会下载这种小工具。

**接下来发生的：**
- 时间和热情都白费。
- 下次有新想法时，**自己内心先打了退堂鼓**——"上次也是这样兴冲冲做完没人用"。

**用户真正的诉求：**
> "在我投入精力**之前**，先有人帮我做一遍冷静的可行性评估——市场有没有人做？技术能不能做？商业上跑不跑得通？**不通过就直接否掉**，不要让我浪费时间。"

---

### 痛点 4：进度永远不透明

**场景：** AI 在后台跑，我不知道它在干嘛。

**接下来发生的：**
- 5 分钟看一次终端，怕它卡住。
- 怕它跑偏，浪费 token。
- 怕它跑完了我没注意到，错过了交付时机。
- 最终的体验是：**我在盯着 AI**，而不是 AI 在替我工作。

**用户真正的诉求：**
> "我不在的时候它自己跑，我在的时候用一句话就能知道'现在怎么样了'。所有进度都看得到、可追溯，但**不需要我主动去查**。"

---

### 痛点 5：AI 团队需要"人来主持"

**场景：** 某些 AI 多 agent 工具号称团队协作，但实际上：
- **主对话窗口必须开着**。
- 我必须充当 team-lead，下发任务、协调冲突、做最终裁定。
- 关掉窗口，团队就停摆。

**接下来发生的：**
- 没法在睡觉时让它跑。
- 没法在上班时让它跑。
- 这不是"AI 团队"，是"**AI 帮我打字的会议室**"。

**用户真正的诉求：**
> "团队的运转**不依赖我在场**。我下班关电脑，早上起来看结果。"

**ccteam 当前进展**:
- "用户在场当 team-lead"这一主诉求,由当前的 chat session(IM bot 通过手机随时下指令)+ bg session 已大头解决 —— 用户不需要守着主对话窗口,团队的执行不依赖人在场。
- **webhook ingress 的 HTTP 入口已落地**:daemon web server 挂 `POST /webhook/:project/:token` 端点,外部世界(CI 红 / CVE / PR-open 等)可直接把事件推进来,落成 `.ccteam/webhooks/` 记录 —— 这个入口当前可用。
- **schedule trigger(真 cron)**、以及"webhook 记录 / 定时事件自动 fan-out 成 agent 任务"属**推后的编排层(ccteam-flow)** —— 让定时巡检 / 夜间任务、以及推进来的事件自动 spawn 成多 agent 工作流,要等编排层落地才完整。

---

### 痛点 6：多个 code agent 各自为战，不按特长串联

**场景：** 我手上同时开着好几个 AI 工具——不同 agent 各有所长：Codex 写实现又快又稳、Claude Code 擅长出架构方案和画原型、Gemini 创意发散最野、Grok 能实时搜最新资料。一个真实任务往往要把它们**接力**起来用。

**接下来发生的：**
- 我先在一个工具里发散创意，再手动把结论复制进另一个工具让它出架构和原型，再把方案搬到第三个工具去写实现，最后又开一个去搜实时资料佐证。
- 每一次"搬运"都靠我手动复制粘贴、对齐上下文——产物在工具之间根本不流动。
- 我成了一个**多模型调度员**：记着哪件事该交给谁、谁的产物该喂给谁——本该是它们各展所长，结果是我在它们中间当人肉传送带。

**用户真正的诉求：**
> "我只想从一个入口提需求，系统自己按任务特长派给最合适的 agent，并且自动接力——创意 → 架构 / 原型 → 实现 → 搜索佐证，一条流水线串下来。我不想自己当'多模型调度员'。"

**与痛点 11 的区别——异构协作 vs 同质并行：**
- 痛点 6 = **按特长跨 vendor 串联 / 分工**（异构协作）——不同 agent 各擅长一段，接力把一件事推进。
- 痛点 11 = **同一件事多路并行加速**（同质并行）——把一个大项目切成 N 个独立子模块同时做。
- 一个讲"谁最适合做这一段"，一个讲"这一段能拆几路一起跑"，互不替代。

---

### 痛点 7：每个新项目都从零开始

**场景：** 做完了项目 A——踩过的坑、找到的好用的库、形成的代码模式——到了项目 B 全部清零。AI 又一次从头摸索，又一次踩同样的坑。

**用户真正的诉求：**
> "我做的项目越多，下一个项目应该**越快、越稳**。经验应该自动沉淀，不需要我手动写 wiki。"

---

### 痛点 8：关键节点不把控 = 终态发现方向错了

**场景：** 把"做个本地书签管理器，离线可用"扔进系统，关电脑出门一周。回来一看——

它给我做了个**带云同步、多用户、有评论功能**的书签平台。测试全绿、文档齐全、技术上挑不出毛病。

**但这不是我要的。**

**接下来发生的：**
- 一周时间已经烧完，token 也烧完。
- 要么接受这个偏方向的产品，要么让它推翻重做（再烧一周）。
- **关键是：plan 阶段它写"将实现云同步"的时候，如果有人/有 agent 拦一下，整周浪费就避免了。**
- 测试通过抓不到这种偏差——测试只验证"代码做了它声称要做的事"，不验证"它声称要做的事是不是用户想要的"。
- 单个 critic agent 也抓不到——它模仿"通用品味"，抓不到我对"我那个产品"的具体期待。

**为什么单 agent 抓不住、必须靠"团队议事"**：用户脑里有个**只有自己知道的 mental model**——"我要的那个书签管理器是什么样"。AI 看到的是文字 spec（spec 永远不完整，人脑里那个东西无法完整文字化）。这不是模型能力问题，是**信息论意义上的下限**——再强的单 agent 也只能从 spec 推断方向，推断本身就是猜测。但**如果换成多 agent 互检**——架构师审技术、CEO 审商业、设计师审 UX、安全官审风险——多视角各自推断，互相挑刺，**绝大多数偏差能在 agent 之间议出来；议不出共识的，才是真正需要用户拍板的**。

**与痛点 5 的区别——离场 ≠ 失联**：
- 痛点 5 拒绝的是「**持续在场当 team-lead**」（每 phase 都问"下一步做啥"）。
- 痛点 8 拒绝的是「**完全失联**」——一周内不出现一次，结果跑偏一周才发现。
- 中间地带 = **AI 团队替人开会，开不出共识时再用 30 秒推用户拍板**。

**用户真正的诉求：**
> "我不想全程在场，也不想睁眼一看不是我要的。系统应该自己有'多人审'机制：架构师审技术、CEO 审商业、设计师审 UX、安全官审风险——这些 AI 视角议出共识就过；议不出共识时，再用 30 秒推给我决策。**不是每个节点都来烦我，而是系统先开会一遍，开得出共识就走，开不出来就把 2-3 个选项摆给我点。**"

**对比佐证（gstack 等工具）**：市面上的 AI 工程辅助工具（典型如 [gstack](https://github.com/garrytan/gstack)）显式拆出 `/plan-ceo-review`、`/plan-eng-review`、`/plan-design-review`、`/ship` 四个独立命令——证明 plan 完成与 ship 前确实是不可绕的关键节点。但 gstack 要求**用户在场敲命令**——回到痛点 5。ccteam 的方案是把这个共识反过来用：**多 agent 自己跑 ceo-review / eng-review / design-review，议得出共识就过；议不出来才主动 push 用户 30 秒决策**。保留了"关键节点必须把关"的实质，删掉了"用户必须在场"的形式。

**系统设计应满足的形态（三层纵深防御）**：
- **L1 架构约束（写死的红线）**：scope budget、phase 必产出物、危险命令拦截、不可改的 invariant——deterministic、不与 agent 商量
- **L2 多 agent 互检（替代人值守的主力）**：每 phase 启用相关 audit agent（architect / critic / designer / security / scope-watcher），议出共识就过——这层处理 95%+ 决策
- **L3 用户 fork 决策（兜底）**：agent 集体拍不了板时主动 push；24h 不响应默认通过；用户 30 秒看摘要 + 点 ABC + 可选一句话 tweak；可调 agent 自信阈值（yolo / balanced / careful）
- **顺序是 L1 → L2 → L3，不是并联**——人是 last resort，不是 first checkpoint。痛点 8 的解法主路径是 L1+L2，L3 只是兜底。

### 痛点 9：工作流插件靠人手动调，效率低还调不全

**场景：** 用了一套像样的 AI 工程辅助工具——比如 [gstack](https://github.com/garrytan/gstack) 的 23-skill 工程团队包，或者 Claude Code 官方 [claude-plugins-official](https://github.com/anthropics/claude-plugins-official) 的几十个 plugin（`feature-dev` / `pr-review-toolkit` / `security-guidance` / `code-modernization` / `code-simplifier` / ...），还能加上社区的若干。

每个工具单独看都很好用：`/plan-ceo-review` 让 AI 站 CEO 视角审；`/plan-eng-review` 站架构师视角审；`/qa` 跑端到端测；`/cso` 做 OWASP + STRIDE 安全审计；`/canary` 灰度发布；`/document-release` 出文档；`security-guidance` 拦危险写文件；`silent-failure-hunter` 揪静默失败……

**接下来发生的：**
- 做完 plan，**忘了**跑 `/plan-eng-review` → 架构没审就 implement，埋雷。
- 记得跑 `/qa`，但**忘了** `/cso` → 上线后被人扫到 SQL 注入。
- 跑了 `/plan-ceo-review`，产物落在某个文件里——**没人**自动喂给 implement 阶段，得我**手动复制粘贴**。
- 项目临近交付，**没人**提醒跑 `/document-release` → 文档缺失，后续移交困难。
- 看到一个新插件叫 `/silent-failure-hunter`，挺有用，但**不知道该插在哪个 phase**——干脆不用了。
- 我加班把所有命令背下来、记每个在哪个 phase 用、记每个产物去哪里……

**等等——这不就是又当了一回 team-lead 吗？**

每个工具都解决一个具体局部问题，**但工具集体留了一个未解决的整体问题：谁来编排它们**。默认答案是"用户编排"——把"协调 agent"换形态变成"调度 plugin"，本质还是用户在做编排劳动。

**与痛点 5 的区别——劳动维度不同**：
- 痛点 5 关切的是**决策劳动**——team-lead 协调冲突、做最终裁定。
- 痛点 9 关切的是**流程编排劳动**——orchestrator 决定"何时调谁、产物给谁、有没有漏掉关键 step"。
- 痛点 5 不解决，人持续在场做**决策**；痛点 9 不解决，人持续做**记忆 + 触发 + 产物搬运**。
- 两个都是"人的劳动"，但**痛点 5 累在精神，痛点 9 累在记忆与流程**——互不替代。一个 AI 工具可能解决了痛点 5 但完全没碰痛点 9（甚至加剧——给了你 23 个新插件让你记）。

**用户真正的诉求：**
> "我不想记几十个命令、不想知道哪个在哪个 phase 用、不想手动把 phase A 的产物复制到 phase B 的输入。**整套工作流应该自己串起来——我提需求，系统自己知道下一步该 review、该 qa、该 cso、该 ship，顺序对、覆盖全、产物自动接力**。新插件出来时，系统自己判断该装到哪个 phase——不用我研究文档。"

**生态视角——这个问题只会更严重**：
- gstack 23 skills 只是开始；claude-plugins-official 几十个、社区还在持续增长。
- 越多好工具 = 越多需要编排的零件 = 用户编排负担**线性增长**。
- 不解决这个，就出现"工具越来越好但用户用不起来 / 用不全"的怪现状——好工具变成沉默资产。

**ccteam 设计的回应**：
- 9 个主干 phase 模板就是预编排好的 workflow 骨架。
- phase 协议须支持"sub-skill 自动调度"——每个 phase 在 front matter 列出本阶段应 trigger 的 sub-skills（例：ship phase 自动跑 `/cso` + `/document-release` + `/canary`）。
- ccteam 的差异化**不是**再写一遍那些 skill，**是替人 orchestrate 这些 skill**——复用 gstack / claude-plugins-official / 社区插件，调用时机由 orchestrator 决定。

### 痛点 10：定制个人工作流，缺好用的模板和 skill 等工具

**场景：** 每个人的工作流都不一样。我想把自己那套固定流程固化下来反复用——比如"每天爬 X → 总结 → 发到 Y"，或者一套属于我自己的开发 / 运营节奏。

**接下来发生的：**
- 翻现成模板 / skill：要么压根没有我要的，要么太通用、套不进我的具体流程，要么得从零拼。
- 想自己拼一套：发现要手写 YAML、要懂配置格式、要理解一堆术语——本来只是想把流程固化一下，结果变成一个小工程。
- 最后要么凑合用一个不趁手的通用模板，要么干脆放弃固化，每天手动重复同样的步骤。

**用户真正的诉求：**
> "给我一批开箱即用的模板，再让我能用自然语言定制、扩展自己的 workflow 和 skill——把'每天爬 X → 总结 → 发 Y'这种流程一句话说清楚就能固化成可复用的 team，不用手写 YAML 或代码。"

**与痛点 9 的区别——定制供给 vs 运行编排：**
- 痛点 9 = 已有一堆工具 / 插件，缺的是**运行时谁来编排它们**（何时调谁、产物给谁）。
- 痛点 10 = 缺的是**定制自己工作流的原材料**——开箱即用的模板库 + 能自然语言扩展的 skill 工具。
- 一个讲"现成零件怎么自动串起来"，一个讲"我这套独特流程从哪来、怎么低门槛造出来"。

### 痛点 11：大项目串行慢，并行规模选不对

**场景 A（项目过大，默认串行太慢）：** 提需求"做一个完整的 SaaS：后端 API + 前端 dashboard + 移动 app + 用户文档"。

ccteam 跑了一周——一个 implement phase 串行做完后端，再切前端，再切 mobile，再切文档。我看着进度条想：**这四件事明明可以并行**，加起来三天就够了。

**场景 B（项目太小，默认并行又浪费）：** 提需求"做个 todo list，本地存 SQLite"。

ccteam 主动开了 4 个 tmux session 并行——后端 1 个、前端 1 个、tests 1 个、docs 1 个。结果总 token 翻 4 倍，代码反而更乱（子模块边界过早划开，接口对不齐）。**这点活根本不需要并行**。

**问题的本质：**
- Claude Code 提供三档并行机制（subagent / Agent Teams / 多 session），粒度从小到大。
- 用户不该知道何时用哪个——但**必须有人决定**，否则要么慢要么浪费。
- 默认串行：大项目太慢；粗暴 always-parallel：小项目资源浪费。

**与痛点 8 L2 的区别——质量并行 vs 速度并行（很容易混）**：
- 痛点 8 L2 = 多 agent **同一输入不同视角议事**（垂直，为正确）——3 个 agent 看同一份 plan 各提意见。
- 痛点 11 = 多 agent **各做不同事**（水平，为加速）——3 个 agent 各写一份不同代码模块。
- 同样"多 agent"，但前者并行**审同一件事**，后者并行**做不同事**；不能混用一种机制兼顾两者。

**项目内 vs 项目间的区别**：
- 多项目并发 = 多个独立项目排队推进（inbox 调度，项目间并发）。
- 痛点 11 = 1 个大项目内部拆 N 路加速（单项目内并行结构）。

**与痛点 9 的区别——并行 vs 串行**：
- 痛点 9 = 串行 workflow 接力（plan → review → ship，不漏不错）。
- 痛点 11 = 同一 phase 内不同子任务并行（implement = backend ∥ frontend ∥ mobile）。

**用户真正的诉求：**
> "我提需求，系统自己评估这事多大、能拆几路、用什么粒度的并行。简单的就串行做，中等的 phase 内并行，大型的开多 session。**我不要知道'subagent vs Agent Teams vs 多 session'是啥——我只要进度合理快、token 不浪费**。"

**关键洞见——三档不是互斥，而是叠加层级**：

很多人误把三档当 either-or 选择。事实上**它们是叠加层级**：

| 项目尺度 | 主框架 | 叠加层 1 | 叠加层 2 |
|---|---|---|---|
| 大型（多子模块） | `multi_session`（每子模块独立 session） | `Agent Teams`（每 session 内 phase 多角色） | `subagent`（每 agent 内研究 / 单点 audit） |
| 中型（单 session 多角色） | `Agent Teams` | `subagent`（每 agent 内研究） | — |
| 小型（单线） | `solo` | `subagent`（偶尔研究 / 单点 audit） | — |

具体例子：implement phase 启动 Agent Teams，`backend-dev` / `frontend-dev` / `reviewer` 三 agent 并行；**backend-dev 内部**同时用 `Task` 工具启 subagent 研究"我们 codebase 怎么用 SQLAlchemy"。两者**同时发生**，职责互不重叠——Agent Teams 做**横向多角色**，subagent 做**纵向 context 节流**。三档机制可以**逐层嵌套**，不是 either-or。

**ccteam 设计的回应**(workflow.yaml 架构,并行拓扑由**推后的编排层(ccteam-flow)**执行):
- **workflow.yaml 声明并行拓扑** — 每个 agent 的 `parallelism: u32` 字段决定该 role 同时可跑几个 session;`trigger: watch:<dir>/` 决定 fan-out 触发条件(每个新 artifact 一个 session)。系统**事件驱动**,无需在 plan 阶段预先决定"主框架"档次。
- **subagent 不在 workflow 协议中声明** — 任何 agent 内部都可 ad-hoc 启 subagent(`Task` 工具),不需要 workflow.yaml 许可,叠加在主框架之上。
- **三档自然落到 workflow 语义**:
  - **solo** = `parallelism: 1` + 串行 watch dir
  - **agent_team** = 同一 watch dir 多 role 监听(fan-out 一次 → N agent 并行处理) + 后续 gate trigger 收敛
  - **multi_session** = 同一 role `parallelism > 1`(同时跑 N session 处理 backlog)
- **资源约束**:`workflow.yaml::budget` 的 `max_cost_usd_per_24h` / `max_agent_spawns_per_hour` 自动 trip + auto-disable;daemon 全局 `MAX_CONCURRENT_PROJECTS` 硬上限。(budget trip → auto-disable 这套自动巡检属**推后的编排层**。)

**边界 — 这条不解决什么**:
- 不解决**自动任务分解**(workflow.yaml 拓扑要 ccteam-creator skill / 人手工写) — 本痛点假设 workflow.yaml 已声明好 fan-out 拓扑。顶层 `squad: { leader, members, hop_limit }` 块提供**跨 session 运行时路由** —— leader 在运行时挑哪个 member 接活(写 `<member>--*.md` artifact),按文件名前缀 dispatch(此运行时 dispatch 属**推后的编排层**)。membership 仍**静态声明在 workflow.yaml**(可审计、不开 prompt-injection 面),解决的是**运行时 dispatch**,**不是**自动 decomposition —— 这条边界仍成立。
- 不解决**子模块接口同步**(role 之间通过 artifact 文件协作,无 RPC/IPC 内层契约管理)。

### 痛点 12:Claude Code(以及任何单体 AI 助手)做不了真大型软件系统(目标)

**用户场景**:
> "我能用 Claude Code 写个 todo CLI、做个 Telegram bot、修个小 bug。但我手上是一个 100k+ LOC 的电商后台 / 实时交易系统 / 多服务架构 — Claude Code 单 session 跑半小时 context 就漂,改完 OAuth 模块忘了 mobile 端要同步改 schema,改完一个 bug 引入回归不被发现。我不需要再'对话式 AI 助手',我需要一个 **24×7 跑着的开发团队**,能自己做 N 周长跑、能多 agent 在多模块并行不踩对方脚、能自己跑回归、能撞到不会的 stack 自己换路。"

**问题本质**:**Claude Code 是会话式工具,不是自助运行的开发团队**。它优秀地解决单次"我提问 + AI 回答 + 我审 + 我接受"的小循环,但有三个根本限制:
- **单 session 上下文容量有限**(即使 1M 也撑不过几天的工作流);长 session 必然 context drift
- **没有并行机制**:多个独立子模块要改 → 用户串行问 → 等;Agent Teams / subagent 只在单 session 内部并行,跨 session 协作要用户手工 orchestrate
- **没有持续运行的"团队感"**:无 daemon 长跑、无 24h 自动 budget、无 agent 之间的稳定 artifact 协议、无 fix-loop escalation 机制

**ccteam 的回应 — Token Maxxing**:**把"用户 + 单 AI 助手"形态升级成"用户 + 多 agent 自助团队 + 7×24 daemon"**。核心机制:
- 投足够 token(预算管理 + budget shaping 不止 trip + disable,而是 throttle/reprioritize)
- 多 agent 并行 + workflow.yaml fan-out + artifact-driven 协作 → 把大问题切到 N 个独立子模块
- 长跑 daemon + meta-agent 总管 → 撞死路自己换 stack 试 / 撞不会的 RFC 自己研究
- artifact 文件 + progress.jsonl 是跨 session 的"团队共识"载体,context 漂掉无所谓 — 下个 spawn 读 artifact 就有共识

**长跑维护方向的当前进展**:
- **vendor-seam forward-compat**(`vendor_compat::warn_unknown_vendor_token` warn-once;未知 Claude job state → 非终态续 probe,未知 Codex event → skip + warn)让上游 CLI 节奏外的新字段 / 新 enum 值不把 daemon 干 panic —— 这服务"长跑可靠性",当前可用。
- **webhook ingress** 的 HTTP 入口当前可用(daemon web server 挂 `POST /webhook/:project/:token`,外部 CI 红 / CVE / PR-open 事件可直接推进来)。
- **真 cron(定时巡检 / 夜间依赖升级)**与"外部事件 → 自动 spawn 修复 agent"属**推后的编排层(ccteam-flow)**。
- **距"≥7 天连续自助跑"目标仍有距离** —— 关键缺口在 budget shaping / 跨模块语义同步(见上)+ 整个自主编排循环要等编排层落地。

**目标**:
- 能让 ccteam **连续自助跑 ≥7 天**做一个真实项目(20-100k LOC,有 DB + API + frontend + e2e test),期间用户 ≤5 次拍板
- 期间产物能 ship(测试通过 + lint 通过 + deploy 通过 + 无回归);token 预算用户可配 + 撞 cap 优雅 throttle 不爆
- **维护**也能跑:对已 ship 的项目持续跑 bug 修复 / 依赖升级 / 性能优化 / 安全补丁(meta-agent 自己识别 issue → 调度 agent 修 → 提 PR)

### 痛点 13：code agent 的强大能力，非技术用户用不上

**场景：** code agent 其实能干的远不止写代码——它能调 API、跑脚本，几乎能自动化任何"目标 + 多步骤"的活。我做产品 / 运营 / 研究，手头一堆这样的活，看着这些能力直流口水。

**接下来发生的：**
- 一上手就被形态挡在门外：是个 CLI，得装环境、配 PATH；要懂 git、懂仓库、懂一堆术语。
- 文档里全是工程黑话，每一步都假设我已经是开发者。
- 这些能力明明能帮到我，但**门槛把我这种不写代码的人整个挡在外面**——能力在那儿，我够不着。

**用户真正的诉求：**
> "我用自然语言（从 IM / web）就能驱动它，不需要懂任何技术细节——不用装环境、不用懂 git、不用学术语。把'目标 + 多步骤'说清楚，它就替我跑起来。"

**与痛点 14 的区别——受众 vs 领域：**
- 痛点 14 讲的是**领域**——把自动化从编程拓到研究 / 运营 / 投资等其他领域。
- 痛点 13 讲的是**受众**——让非技术的人也能用上（即便还在编程相关的活上）。
- 一个扩"能做什么样的活"，一个扩"谁能用得动"；两者呼应但不同。

### 痛点 14:自动化只服务"开发软件",拓不到其他领域(目标)

**用户场景**:
> "AI 自动化只解决了'写代码'。我做研究 / 内容运营 / 投资分析 / 实验室自动化 — 这些也是'目标 + 多步骤 + agent 之间协作'的工作流,凭什么没有同样的自助团队?Claude / Cursor / Codex 都只配了'编程域'的工具(Read/Edit/Bash),没人给我配'研究域'的工具(scrape / paper search / dataset / 回测引擎),也没人教 LLM 怎么编排研究流程。"

**问题本质**:**自动化工作流系统当前全部锁死在编程域**。但"目标 + 多步骤 + agent 协作"是通用模式 — 研究、运营、投资、实验室、法务、客服都符合。锁死在编程域是因为 AI agent 默认工具集(Read/Write/Edit/Bash + git)只方便操作"文本文件 + 命令行" — 这恰好覆盖编程,不覆盖其他。

**ccteam 的回应 — 数据驱动的领域抽象**:ccteam-core 从设计上**零编程域字面量**(strategic doc §1 红线):workflow.yaml + team.yaml + `.claude/agents/<role>.md` + MCP 工具接入 = 任何领域可创建自己的多 agent 团队。Token maxxing 让"对话式 wizard 创建领域 team"也变成 N 分钟级体验。

**目标**:
- 出 **3 个非编程领域的官方 team**(候选:研究 / 内容运营 / 投资分析,各自 starter workflow.yaml + agents + MCP 工具集)
- **用户能在 30 分钟内**用 `ccteam-creator` skill + 对话式 wizard 创建自己领域的 workflow / agent 拓扑 → 不需要懂 YAML / Rust,自然语言对话定义
- 跑通第一个**非编程**项目(典型:用户描述"我想跑一个每天爬 5 个财经网站 + 写一篇市场摘要 + 发到 Telegram 的工作流",30 分钟内 ccteam 跑起来)

## 三、用户对"理想体验"的描述

如果让目标用户用一句话描述他想要的工具，他会说：

> **"我说一句中文，它给我一个能跑的软件。中间它不来烦我，除非真的需要我做选择；选择题给我两三个选项 + 它的推荐，我点一下就行。"**

更具体的体验拆解：

| 维度 | 用户期望 |
|---|---|
| **输入** | 一句自然语言，不需要技术词汇 |
| **输出** | 可运行的软件 + 测试报告 + 进度记录 |
| **过程参与度** | 几乎为零；仅在 AI 自检拍不了板或系统主动 escalate 时出现 |
| **决策频次** | 极低——AI 自检处理大多数；用户上推典型 0-2 次/项目 |
| **AI 自检层** | 多 agent 互检（architect / critic / designer / security / scope-watcher）+ 架构约束（写死的红线）；agent 议出共识就过——这层处理 95%+ 决策 |
| **工作流编排** | 系统自己串主干 phase + sub-skill 自动 trigger + 产物自动接力；用户只提需求，不需要触发任何命令、不需要记任何工具放在哪个 phase |
| **并行规模** | workflow.yaml 声明 `parallelism: u32` + `trigger: watch:<dir>/`,fan-out 事件驱动;subagent 任何粒度都可叠加;用户不感知"何时用哪档" |
| **用户兜底层** | agent 议不出共识时 push：摆 2-3 个选项 + 推荐 + 一句话 tweak；24h 不响应默认通过；可调 agent 自信阈值（yolo / balanced / careful） |
| **失败处理** | AI 自己尝试 N 轮后才来找我，并附"试过什么 / 卡在哪" |
| **多项目** | 排队执行，自动推进，不需要我手动调度 |
| **离线运行** | 我关电脑/窗口，AI 团队继续开会——议不出共识时 push telegram 等我 30 秒拍板 |
| **质量保证** | 多 agent 互检 + 测试不过不交付；方向由 AI 团队议事保证，议不出来才上推我 |
| **无效想法** | 在投入开发**之前**就被否掉，附理由 |
| **跨项目沉淀** | 项目 N+1 比项目 N 更快、更稳，自动复用经验 |

## 四、非目标用户（明确不服务的人）

为了让边界清晰：

- **想用 AI 学编程的人**：ccteam 是交付工具，不是教学工具。
- **企业级团队**：复杂权限、合规、多人协作的场景不在范围内。
- **追求精雕细琢的工程师**：希望对每行代码有控制权的人，会觉得 ccteam 太"黑盒"。

## 五、成功判定（用户视角）

ccteam 是否成功，**不**由这些指标判断：
- ❌ 代码行数
- ❌ Agent 数量
- ❌ 技术架构先进度

**而是**由这些指标判断：

1. **从想法到上线，用户参与时间 < 10 分钟**（不含 AI 自己跑的时间；含 fork 决策时间）。
2. **一周内能并行推进 5+ 个项目**，用户不感到混乱。
3. **用户睡觉时项目继续推进**，醒来有具体进展。
4. **失败的想法在投入开发前被识别**，用户不会感到"白做了"。
5. **用户做的项目越多，下一个越快**——经验自动沉淀，无需手动整理。
6. **方向不跑偏**——多 agent 互检拦住绝大多数偏差；agent 议不出共识时，用户 30 秒拍板。终态不出现"交付的不是我要的"。
7. **零编排负担**——项目从想法到交付，用户不需要 trigger 任何 phase / skill / plugin；新工具出现时，系统自己判断该装到哪个 phase。
8. **并行规模合理**——大项目自动多 session 加速、小项目串行不浪费；solo / Agent Teams / 多 session / subagent 三层叠加由系统自动决定，用户不感知。

## 六、与"AI 团队编排工具"的根本差异

市面上已存在让用户**主持** AI 团队的工具（典型如 ccteam-creator）。它们的定位是：
> "**人类掌舵**，智能体执行。"

ccteam 的定位是：
> "**用户提需求，AI 团队替你议事并执行；议不出共识时你 30 秒拍板。**"

| 维度 | AI 团队编排工具（如 ccteam-creator） | ccteam |
|---|---|---|
| 用户角色 | Team-lead（必须在场） | 需求提出者 + agent 议事僵局时的拍板者（典型 0-2 次/项目） |
| 决策频率 | 高（每阶段都需要） | 极低——AI 自检层处理 95%+；仅 agent 议不出共识时弹 |
| 决策成本 | 每次都要看上下文、做判断 | 30 秒：看摘要 + 点 ABC + 可选一句话 tweak |
| 关掉窗口 | 团队停摆 | AI 团队继续开会（议不出共识时推 telegram 等用户） |
| 多项目 | 用户手动切换/调度 | 自动排队推进 |
| 想法可行性 | 用户自己判断 | AI 自动评估，否掉无效想法 |
| 方向校准 | 持续在场把控 | L1 架构约束 + L2 多 agent 互检 + L3 用户兜底（三层纵深防御） |
| 工作流编排 | 用户手动调命令（知道哪个何时用、产物怎么接） | 系统预编排 phase pipeline + sub-skill 自动 trigger + 产物自动接力；新工具加入由 ccteam 决定挂载点 |
| 并行规模 | 用户手动决定单线 / 多线、何时开多 session | workflow.yaml 声明 `parallelism: u32` + `trigger: watch:<dir>/`,事件驱动 fan-out;subagent 可叠加 |
| 经验沉淀 | 项目内文档 | 跨项目自动复用 |
| 目标用户 | 想当 team-lead 的人 | **不想**当 team-lead 但**仍要在 AI 团队议不出来时拍板**的人 |

**一句话总结：**
ccteam-creator 帮你**当好一个 team-lead**；ccteam 让你**不当 team-lead——AI 团队替你开会议事，议不出共识时你用 30 秒拍板**。把"持续主持"换成"偶尔仲裁"。

**关键认知（避免捡芝麻丢西瓜）**：
- 旧方案的真实价值是"**人持续在做品味与方向校准**"。把人移走的同时必须保留这部分价值——否则解决了痛点 5 却制造了痛点 8。
- ccteam 的设计公式不是「全自动 vs 人控」二元对立，而是「**L1 架构约束 + L2 多 agent 互检 + L3 用户最终 fork**」三层纵深防御。前两层让 95%+ 决策 AI 自决——这 95% 不靠"AI 听话"实现，靠**多 agent 视角互相挑刺 + 红线写死**实现。
- 人在最后一层出现 30 秒，**只在 agent 拍不了板时兜底**。痛点 8 的解法主路径是 L1+L2，**不是 L3**——L3 是 last resort，不是 first checkpoint。

## 七、本文档的边界

本文档**不**讨论：
- 具体的 agent 角色和数量
- 文件协议、消息队列、控制平面的实现
