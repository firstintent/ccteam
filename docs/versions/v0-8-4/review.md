# v0.8.4 合理性审查

> 对 v0.8.4 需求(3 硬阻断)与 `prd.md` 设计做一次"该不该做 / 做多少 / 怎么定级"的批判性审查。**结论先行,逐条带据,含真实 pushback。**

## 结论(TL;DR)

- **B2 分片** = 必做,零争议(这是 correctness bug,不是 feature)。
- **B3a 入站图文** = 高价值,保留。
- **B1 进度** = 合理,但实现要**分级**(先极简、再 live-edit),且它治不了"单个长步骤内的静默"。
- **B3b 出站文件** = 本批合理性**最弱** + 最重 + 唯一带未解设计题 → **建议本版后置**。
- 这是一个 **minor 体量(应按 v0.9.0 强度规划)**,标成 patch 易低估。
- 修完这 3 项是"**去掉让它不可用的几件事**",**不等于"丝滑替代 TUI"** —— 别对外这么说。

---

## 逐功能点审查

### B2 长消息分片 —— ✅ 必做,无争议
静默丢数据是 **correctness bug**,不是体验问题:一个 diff/长解释 >4096 直接消失、只 warn-log。单这一条就值一个 release。零异议,优先发。

### B3a 入站图文 —— ✅ 高价值,保留
"贴报错截图给它看"是真实高频日常需求;官方插件能、ccteam 不能 = 明确退步。落盘 + 给 Read 路径的方案干净、不污染上下文。保留。

### B1 进度可见 —— 🟡 合理,但价值/成本要分级
- **价值真实**:一条长 turn 期间 TG 全静默,是劝退点。
- **但要清醒**:
  1. 它是 **UX polish,不是 correctness**(不修也"能用",只是难受);
  2. `live-edit + 节流 + 状态机`是最贵的 20%;
  3. 粒度 = "**步骤完成**"。一条 2 分钟的 `cargo test` 仍是**跑完后**才显示一行 —— 那 2 分钟内**照样静默**。
- ⇒ B1 治的是"**多步骤 turn 的整体黑盒**",治不了"**单个长步骤内的静默**"。
- **建议**:P1 先上极简版(合并的 `🔧 ran: X` 进度行,几条新消息),把 live-edit + 节流作为 P1.5 迭代,不必一步到位押全部复杂度。

### B3b 出站文件 —— 🟠 合理性最弱,建议后置
- **频次存疑**:日常开发里"agent 主动发文件给你"用得少 —— 文件通常**写进 repo 你直接看**;主用例是截图回传,偏小众。
- **它恰恰是最重 + 唯一带未解设计题**的一项(MCP socket handler 无 live channel 句柄,见 prd §1.6 / §3-P2b)。
- **建议**:**本版砍掉 P2b**,先发 P0/P1/P2a;P2b 等出现具体拉力(比如真的高频要截图回传)再做。砍掉它 = 移除本版**唯一的实现不确定性**,显著降风险。
- 注:用户在 gap 分析里确实列了"拿不回文件",所以这是**排序**建议(后置),不是否定。

## 更大的三个合理性问题

1. **版本定级偏低**。3 功能 / 4 phase / 新 `Channel` trait 方法 / 新 MCP 工具 / 跨 `transport+gateway+daemon` 的附件管线 —— 按项目自己的 `patch(V0.x.y)` vs `minor(V0.x.0)` 区分,这是 **minor 体量**。可保留 `0.8.4` 号,但**按 minor 强度走**(wave 化、每 wave handoff),否则当 patch 规划会低估。

2. **这大半是"补插件已有的能力",不是创新**。B2 + B3 ≈ 和你正在用的官方 telegram 插件**拉平 parity**,不是净新增价值。这本身合理 —— 自建 gateway 必然要自建 channel 层,才能承载 ccteam 真正的差异化(多项目路由 / 多 vendor / 成本预算 / `@bot` 跨会话)。但要清醒:**v0.8.4 大半在"赎回自建 gateway 丢掉的 parity"**。真正差异化是 **B1 的多 vendor 统一进度 + 路由**那部分。

3. **修完 ≠ 丝滑替代 TUI**。gap 分析是 6 项 + setup 摩擦,本版只修 3 个 output/IO 项。**v0.8.4 之后仍未解**:
   - 无 HITL 审批(有人没审批门不敢日用 `rm -rf` 级操作);
   - 错误回显不一致(本版仅顺手修"分片/发送失败"一处);
   - Codex `/clear` `/new` 缺、exec 每 turn fresh context;
   - **6 步 setup 摩擦**(`init` ≠ 能聊的 bot)—— 这条对"日常采用"其实比图文更早撞墙。
   - ⇒ 把 v0.8.4 定位成"**去掉让它不可用的几件事**",而非"达成丝滑"。下一步真正提升采用率的,可能是 **setup 一键化** > 出站文件。

## 需求清单里漏掉、但该一起修的

- **`"submitted s{n} turn {id}"` 机器人 ack**:今天每条消息在真答案前先回一句机器味 ack,本身就是噪声/反丝滑。PRD 已把它折叠进 B1 的 status 种子(好),但你原始 3 条清单没列它 —— 它其实是**第 4 个微阻断**,顺手一并修掉(B1 落地即顺带解决)。

## 推荐的本版范围(我的建议)

> **P0 分片 + P1 进度(可先极简) + P2a 入站图文 + 干掉 ack 噪声;P2b 出站文件后置。** 按 minor 强度规划(wave 化)。这样:止血(P0)、治黑盒(P1)、高价值入站(P2a)全拿,同时**移除唯一的设计不确定性(P2b)**,本版可控可发。

> 若坚持本版含 P2b:把它放最后、独立 PR、先确认 MCP→channel 可达性再动手(prd §3-P2b 候选 A 兜底)。
