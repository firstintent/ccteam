一个 Gateway 路由核,两条平行的用户进入层

v0.8.1/8.2 已把 IM 做成"进入层 → Gateway → session"。v0.8.3 不另起炉灶:web 复用 同一个 Channel trait,作为一条 channel="web" 的 transport 接进同一个 Gateway。IM 和 web 自此对称。

   Telegram · Slack · 微信 · 飞书                 浏览器 (web console)
        │  Channel impl                              │  ccteam-chat.v1 WebSocket
        │  transport/providers/*.rs                  │  ccteam-web::routes::chat_ws  (新)
        └───────────────────┬────────────────────────┘
                            ▼   线缆 = ChannelMessage / SendMessage 的 JSON 镜像
              ┌───────────────────────────────────────┐

              │  handle_text:  @bot · /new · /use · /cd  │
              └────────────────────┬──────────────────┘
                                   ▼ submit_turn / events
                  Claude · tmux     ·     Codex · app-server
                  (HarnessAdapter × ProcessBackend,不动)

为什么 web 也是"终端"

和 IM 同构:一个浏览器 chat = 一个终端 —— 跨多 project、随时 /new 多 session、随时切。区别只在外壳(浏览器 vs 手机),路由核与执行层同一套。

net-new 极小

几乎全是复用:Gateway / 路由 / adapter / event pump / 出站 / WsChannel / pty_ws 都在。新增只有:web 的 chat WS 路由 + cli 层 mpsc 桥 + SPA chat 视图。

web ⊥ im 不破

桥在 cli 层(它本就同时依赖 web 和 im)用 mpsc 接线;ccteam-web 不引入 ccteam-im 依赖,反之亦然。线缆是中立 JSON。
一句话: v0.8.3 = 点亮原型里 im.html「未来⑥」那条 —— 浏览器 ⇄ WebSocket ⇄ 网关,复用 WsChannel(同一 Channel impl),把 web 从只读看板升级成与 IM 平行的进入层。

同一个 session,两个进入层都能进 —— 这就是"平行"

下面手机(Telegram)和浏览器(web)对着同一个 Gateway、同一批常驻 session。在手机起的 session,web 列得出、能接着聊;反之亦然。

子协议 ccteam-chat.v1(与已有 ccteam-pty.v1 并列)

两条 WS 各管一摊:ccteam-pty.v1 = 裸字节终端中继(已有);ccteam-chat.v1 = 结构化对话(新)。chat 帧是 ChannelMessage/SendMessage 的 JSON 镜像 —— 进 Gateway 时无损还原。

Client → Server(入站 → ChannelMessage)

// 普通发言 / 命令 / @mention 全是一条 text 帧
// —— 与 IM 同构:内容原样交给 handle_text 解析
{ "type":"text",
  "content":"@codex 给 /v2/orders 加幂等键",
  "id":"c-1042" }

// UI 点项目/标签 → 显式切换帧(等价 /cd · /use)
{ "type":"switch", "project":"payments", "session":"s2" }

// 附件(随下一条 turn)
{ "type":"attach", "name":"shot.png", "data":"<base64>" }
映射text → ChannelMessage{ channel:"web", chat_id, sender, content } 推入 Gateway inbound mpsc

Server → Client(出站 ← turn 事件 / SendMessage)

{ "type":"turn_started", "session":"s2", "vendor":"codex" }
{ "type":"assistant_delta", "text":"在 thread 上开干…" }
{ "type":"tool", "name":"app-server",
  "summary":"ItemStarted · file_change" }
{ "type":"reply", "content":"已加 Idempotency-Key 中间件。" }
{ "type":"turn_done", "session":"s2" }

// 会话/项目列表(连上 / 变更时推,驱动左栏+标签)
{ "type":"sessions", "items":[ … ] }
// 背压:与 pty_ws 一致的 lag 语义,不断流
{ "type":"lag", "behind":42 }
来源Gateway event pump 的 GatewayEvent / SendMessage(channel=web)→ 桥 → 本 WS
轴ccteam-pty.v1(已有)ccteam-chat.v1(本版新增)
路由/ws/{slug}/pty · /ws/{slug}/{sid}/pty/ws/chat(chat 级,带项目/会话切换)
载荷裸 tmux 字节 + resize 控制帧结构化 turn 事件 JSON(上表)

用途power-user 看完整 TUI日常对话进入层(= IM 体验)

为什么不把 chat 塞进 pty.v1: 裸字节是给 xterm 渲染的,做不了"切 session / @bot / 结构化 tool 行 / 列会话";chat 需要结构化帧。两条 WS 并存、各自最顺,正是"per-adapter best-fit"的同款取舍。

接入缝:browser → ccteam-web → (cli mpsc 桥) → Gateway,web ⊥ im 不破

① 浏览器 + ccteam-webchat WS 路由 + 独立 chat SPAnet-new
新增 routes::chat_ws(子协议 ccteam-chat.v1)。沿用 pty_ws 的 axum upgrade / auth_layer / 背压套路。独立 chat SPA 外壳(不嵌 dashboard 导航;全 session 左栏 + 连续会话流 + composer)。不依赖 ccteam-im。
② cli 层 mpsc 桥run_start daemon 装配处接线net-new(小)
cli 本就同时 spawn web + im。在此把 web chat WS 的入站/出站,经 WsChannel(或等价 mpsc 适配)接到 Gateway 的 inbound mpsc + 出站。线缆 = ChannelMessage/SendMessage JSON。这是唯一让两者相遇的地方,且只在 cli。
③ Gateway 路由核(ccteam-im)handle_text · chat⇄project⇄session · spawn/resume复用 · 不动
channel="web" 的消息走和 telegram 同一条 handle_text:@bot / /new / /use / /cd / submit_turn / event pump / 出站全复用。session 注册表、resume-by-id 不动。
④ 执行层(ccteam-harness)Claude tmux · Codex app-server复用 · 不动
HarnessAdapter × ProcessBackend 完全不感知进入层是 web 还是 IM。submit_turn / events 同一套。
